## C. 운영 반영 전 직접 확인 (화면별)

### C-1. Vercel — 어느 브랜치가 운영으로 나가는지
1. vercel.com → 해당 프로젝트 → **Settings → Git** → **Production Branch** 가 `main` 인지 확인.
2. **Deployments** 탭에서 `main` 최근 배포가 "Ready" 인지 확인(현재 운영 정상 상태 기록).
3. 새 브랜치를 푸시하면 **Preview 배포**가 생깁니다. Preview 는 환경변수(`VITE_API_URL`, `ADMIN_API_TARGET`)가 없으면 설정 오류 화면이 뜨거나 빌드가 실패하도록 설계돼 있습니다(운영 서버로 새는 것을 막는 안전장치). **Preview 실패는 정상**일 수 있고, 운영에는 영향이 없습니다.

### C-2. Vercel — 환경변수 (Settings → Environment Variables)
| 이름 | 운영(Production)에서 | 확인 |
|---|---|---|
| `VITE_IMP_CODE` | 없어도 됨(운영 도메인은 기존 운영 코드 사용) | 값이 있다면 PortOne 운영 가맹점 코드(`imp…`)와 같은지 |
| `VITE_IMP_CHANNEL_KEY`, `VITE_IMP_BLOCKED_CHANNEL_KEYS` | **Production 에는 넣지 않음**(테스트 전용) | Production 항목에 있으면 삭제 대상으로 표시해 두기 |
| `VITE_API_URL` | 없어도 됨(없으면 기존 운영 백엔드) | 있다면 `https://…onrender.com` 형태, 경로 없음 |
| `ADMIN_API_TARGET` | 없어도 됨(운영은 기존 백엔드로 자동 연결) | 있다면 운영 백엔드 주소와 같은지 |
이름만 확인하세요. 값을 채팅이나 문서에 붙여넣지 마세요.

### C-3. Render — 백엔드 서비스 환경변수 (Dashboard → 서비스 선택 → **Environment**)
| 이름 | 필요 | 확인 |
|---|---|---|
| `DATABASE_URL`, `DATABASE_SSL` | 기존 값 유지 | 그대로 있는지 |
| `ANTHROPIC_API_KEY` | 기존 값 유지 | 있는지 |
| `ADMIN_TOKEN` | 기존 값 유지 | 있는지(32자 이상) |
| `PORTONE_API_KEY`, `PORTONE_API_SECRET` | **운영 키** | 있는지. 테스트 키가 아닌지 |
| `GMAIL_USER`, `GMAIL_PASS` | **필수** | 있는지. 없으면 인증번호 메일이 안 가서 재열람이 안 됩니다. (Gmail 앱 비밀번호가 유효한지는 아래 F-4 로 확인) |
| `PUBLIC_SITE_URL` | 선택 | 없으면 `https://www.mysaju.shop` 사용. 도메인이 같으면 그대로 두기 |
| `SUCCESS_CHILD_ENABLED` | **출시 시 `1`** | 배포 직후 결과 확인 후 마지막에 켭니다(D-5). 지금은 **수정하지 마세요** |
| `EXTRA_ALLOWED_ORIGINS` | 운영 불필요 | 미리보기 주소가 들어 있다면 의도한 것인지 |
| `EMAIL_TRANSPORT`, `MYSAJU_TEST_ENV`, `PORTONE_INCLUDE_SANDBOX`, `DISABLE_AI_RETRIES`, `ADMIN_COOKIE_INSECURE`, `SUCCESS_OPS_SWEEP` | **운영에 있으면 안 됨**(테스트 전용) | 있다면 표시해 두고 제거 상담 |
Render 서비스의 **Settings → Build & Deploy → Branch** 가 `main` 인지, **Auto-Deploy** 가 켜져 있는지도 확인합니다. Auto-Deploy 가 켜져 있으면 `main`에 합치는 순간 배포됩니다.

### C-4. 운영 DB 백업 (**백업이 확인되기 전에는 배포 금지**)
먼저 DB가 어디에 있는지 확인: Render **Environment**의 `DATABASE_URL` 값의 서버 이름만 확인합니다(값 전체를 공유하지 마세요).
- 서버 이름에 `render.com`이 포함 → **Render Postgres**:
  1. Render Dashboard → 해당 **Postgres** 인스턴스 → **Recovery**(또는 **Backups**) 탭.
  2. 유료 플랜이면 자동 백업 목록에서 **오늘 날짜의 백업**이 있는지 확인하고, **Create backup / Export** 로 지금 시점 백업을 하나 더 만듭니다(상태가 "Completed"/"Available"이 될 때까지 대기).
  3. 무료 플랜이면 자동 백업이 없습니다 → 아래 `pg_dump` 방식으로 PC에 받아 두세요.
- 그 밖의 서버(Neon, Supabase 등): 해당 서비스의 **Backups/Branches** 메뉴에서 지금 시점 백업 또는 브랜치를 만듭니다.
- 어디서든 가능한 방식(PC에서): `pg_dump "<DATABASE_URL>" -Fc -f mysaju-backup-2026XXXX.dump` 를 실행하고, **파일 크기가 0이 아닌지** 확인합니다. 접속 주소는 터미널 환경변수로만 넣고 파일·채팅에 남기지 않습니다. 백업 파일은 개인정보이므로 안전한 곳에 보관합니다.
- 백업 확인 기준: ① 백업이 만들어진 시각(오늘) ② 상태 정상/파일 크기 > 0 ③ (가능하면) 테이블 목록에 `orders`, `results`, `analysis_jobs` 가 보이는지. **세 가지를 확인한 뒤에 알려 주세요.**
- 추가 확인(읽기 전용 SQL): `SELECT to_regclass('public.reviews');` 결과가 **비어(NULL) 있어야** 정상입니다. 값이 있으면 이미 다른 구조의 `reviews` 테이블이 있다는 뜻이므로 **배포를 멈추고 알려 주세요.**

## D. 배포 순서 (모두 운영자 승인 후)
1. 백업 확인(C-4) 완료 → 알려 주기.
2. `git push -u origin release/launch-final` (브랜치 푸시만, 운영 영향 없음).
3. Render 에서 `main` 이 아닌 이 브랜치가 배포되지 않는지 확인 후, `main` 에 fast-forward 합치기 → Render(백엔드)·Vercel(프런트) 자동 배포. Render 로그에 `테이블 준비 완료` 류 메시지가 뜨고 오류가 없는지 확인.
4. 프런트·백엔드 둘 다 "Ready/Live" 확인. `https://www.mysaju.shop/` 가 새 판매 화면으로 열리는지, `/?policy=privacy` 가 열리는지 확인.
5. `SUCCESS_CHILD_ENABLED=1` 설정(Render Environment 수정 → 자동 재시작) — **마지막에 켜야 합니다.** 켜기 전에는 주문·체험이 거절돼 안전합니다.

## F. 배포 후 확인 순서 (실결제 1건 → 환불 → 체험 코드 → 재열람)
**준비:** 관리자 로그인 방법은 `후기-승인-운영.md`, 체험 코드 발급은 `backend/dev/trial-codes.cjs`(또는 `.ps1`)의 `issue` 명령으로 합니다. 본인 이메일 주소 두 개(결제용 A, 체험용 B)를 준비하세요.

1. **화면 확인(결제 전)**: 홈 첫 화면 문구·50,000원 '출시 기념가'·사업자 정보·정책 링크 3개 확인. 결과지 샘플 보기 정상.
2. **실결제 1건 (A 이메일, 본인 카드, 50,000원)**: 정보 입력 → 결제 전 확인 문구 → 결제 → 1~2분 안에 결과지가 **화면에 바로** 표시되는지. **결과지 메일이 오지 않는지** 확인. 결제 금액 50,000원, PortOne 콘솔에 결제 1건이 보이는지 확인.
3. **후기 작성**: 결과지 맨 아래 후기 남기기(예시: 본인 점검 후기). 홈에는 아직 안 보여야 함 → 관리자 API 로 승인(문서 참고) → 홈 '엄마들의 이야기'에 **구매 인증**으로 표시. (확인 후 필요하면 `hidden` 으로 숨기기)
4. **재열람(유료)**: 홈 '내 결과지 다시 보기' → A 이메일 → 인증번호 메일 수신(Gmail 설정 확인) → 입력 → 결과지 목록 → 열기. **AI 재생성·추가 결제가 없어야 함**(PortOne 결제 건수 그대로, 결과지 내용 동일).
5. **환불**: 환불 가능 시점(결과지를 받기 전/중복·오류 등)은 환불정책을 따릅니다. 확인용으로는 관리자 환불(`POST /api/admin/orders/<주문번호>/refund`, 로그인 쿠키 필요) 또는 고객 화면의 '전액 환불 요청'(결과지 생성 실패로 안내 화면이 뜬 경우에만 노출)을 사용합니다. PortOne 콘솔에서 해당 결제가 **취소**로 바뀌고, 재열람 목록에서 환불된 주문이 **사라지는지** 확인. 고객 이메일로 **환불 완료 안내 메일**이 1통 가는 것이 정상입니다(결과지 내용은 없음).
   - 주의: 결과지를 이미 받은 뒤의 환불은 정책상 제한될 수 있으므로, 환불 점검 전용으로 **결제 1건을 더** 하는 것이 정확합니다(그 경우 결과지 확인 없이 바로 환불 요청).
6. **무료 체험 코드 (B 이메일)**: 체험 코드 1개 발급 → 입력 시 금액 0원·버튼이 '결제 없이 결과지 받기'로 바뀜 → 결과지 생성·화면 열람 → 같은 코드 재사용 시 거절 → 같은 이메일로 다시 체험 시 거절. 후기 작성 시 **무료 체험**으로 구분 표시되는지.
7. **재열람(체험)**: B 이메일로 재열람 → 체험 결과지가 '무료 체험'으로 목록에 보임.
8. **오류 확인**: 틀린 인증번호 입력 시 안내만 뜨고 결과지가 열리지 않음. 모르는 이메일로 인증번호 요청 시 같은 안내가 나옴(이메일 존재 여부를 알려 주지 않음).
9. **정리**: 점검용 후기·주문의 보관/삭제는 `개인정보-수동삭제-운영.md` 기준을 따릅니다. 점검 결제 건(유료)은 거래 기록이라 삭제하지 않습니다.
